# Questions that should change the plan

These are evidence-derived heuristics, not Jan's private thoughts. Jan case IDs (J) refer to `frdel` → `references/decision-cases.md`; use native `skills_tool:read_file`. Maintainer-feedback lesson IDs (L/D) refer separately to `engineering-delivery` → `references/chat-lessons.md`. Use only criteria relevant to the task.

1. **Which owner must remain observable and extensible?** Keep lifecycle and dispatch entry points at their public owner; extract mechanics behind them when useful. Trace implicit decorator paths and plugin callers before moving or deleting a method. Hierarchical hooks address namespace collisions, not merely organization. [Jan J1, J2]
2. **What existing primitive already owns this lifecycle?** Prefer the native initializer, context, module loader or Git operation when it covers the requirement. Compare behavior and failure recovery, not just shorter code. Independent child state can remove a queue; a shared initializer can replace copying mutable configuration. [Jan J3, J4, J5, J6]
3. **Is this mechanism justified by a concrete obligation?** Extra structure is justified for isolation, startup delivery, invalidation or recoverability. Name the failure it prevents and how to test it. Otherwise keep the change direct. The history contains substantial new systems as well as deletions. [Jan J4, J7, J8]
4. **Which runtime actually owns the capability?** Repository code, durable updater, image, installed plugin and host connector can differ. Gate on actual capability and support existing installations; a new checkout does not upgrade a durable executable or open an old image's port. [Jan J5, J9]
5. **Can responsibility move without breaking consumers?** Shared mechanics belong with their real users; domain policy and optional dependencies remain with their plugin. Preserve documented imports and trust boundaries during extraction. An adapter is justified when a real consumer needs it, not for hypothetical flexibility. [Jan J6, J9]
6. **What can fail halfway, and what must survive?** Preserve user state, rollback evidence and cleanup ownership. Native operations reduce custom mechanics but still require recovery and error reporting. Historical stash details are not instructions to run destructive Git commands today. [Jan J5]
7. **Does displayed state tell the truth?** Remove queued states when execution is no longer queued; distinguish configured/default/effective values. Use established UI primitives and vocabulary and verify the actual transition. [Jan J4; feedback D1–D4]
8. **What evidence would falsify the explanation?** Trace the runtime path, measure a suspected bottleneck separately, and discard disproven changes. A tiny targeted fix can be right; a multi-stage system can also be right. No performance multiplier without a comparable measurement. [Jan J7, J10; feedback L3, L5]
9. **What is the confidence and counterexample?** Inspect authorship and subsequent revisions. A single case supports a narrow precedent. Requested innovation, current security needs and current DOX can justify a different choice. [Jan J11, J12]

Before delegation, state the relevant answer, protected invariant and acceptance check in the brief. Reviewers should independently check that the precedent fits; they should not demand historical mimicry.
